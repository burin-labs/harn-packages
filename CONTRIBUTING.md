# Contributing to the Harn package index

This repository serves the public Harn package index. The whole product is one
file, [`harn-package-index.toml`](harn-package-index.toml), published over
HTTPS at <https://packages.harnlang.com/harn-package-index.toml> and used by
default by the `harn` CLI.

A change here is a change to what every Harn user can resolve, so the bar is
different from a normal source repository: the index stores metadata only, and
every entry has to name a tag and a commit that actually exist.

## The normal path is `harn publish`, not a hand-written pull request

Package authors do not edit this file by hand. Running `harn publish` in a
package's own repository tags that repository and opens the pull request here
for you, with the version, tag, and resolved commit filled in.

Open a pull request by hand only to fix an entry that is already wrong, for
example a version pinned to a tag that was never pushed. Say in the description
which published fact the index disagrees with.

## What an entry has to satisfy

Registry v2 binds each version to both its public tag and the full commit SHA
that tag resolved to. That binding is what makes an install reproducible, and
it is why these rules are not negotiable:

- **Versions are immutable.** Add a new version; never rewrite or delete a
  published one. A consumer's lockfile points at what is here today.
- **The tag and the commit have to agree.** The `rev` is the commit the `tag`
  resolved to at publish time, in full, not abbreviated.
- **The repository and provenance URLs point at the package's own repository.**
  The index never hosts source.
- **No secrets, ever.** The index is public and served to anyone.

## Validate before you open a pull request

Run the same validator CI runs, using the Harn version pinned by
[`.harn-version`](.harn-version):

```sh
harn package registry verify harn-package-index.toml \
  --remote \
  --receipt-out registry-verification.json
```

`--remote` is the part that matters. Without it the check validates the file's
shape and passes on an entry whose tag does not exist; with it, the verifier
resolves every tag and commit against the real repository. A schema-clean index
that nobody can install from is the exact failure this repository has already
shipped once, so run the remote check and read the receipt rather than trusting
the exit code alone.

The Harn verifier owns the contract: schema validation, package and version
identity, provenance coherence, immutable tag and commit binding, and remote
resolution. There is no second validator in this repository to keep in sync.

## How a change reaches users

Merging to `main` publishes the index through GitHub Pages at the custom domain
in [`CNAME`](CNAME). A reconcile workflow also runs so a release that shipped
its tag but never reached the index is corrected within minutes rather than at
the next daily run.

If you shipped a release and `harn add` still cannot see it, that gap is the
first thing to check.

## Pull request titles and descriptions

Title every pull request `[Area] Sentence case description`, for example
`[Index] Record @burin/github-connector 0.8.7`. Use one of `Index`, `CI`,
`Docs`, or `Pages`.

Keep the description to three to five sentences: what changed, why, the one
risk, and how you verified it. For an index change, "how you verified it" means
the remote verification receipt.

## Labels

`.github/labels.yml` records the label vocabulary. Priority, status, and effort
come from the org taxonomy in
[burin-labs/.github](https://github.com/burin-labs/.github); `area/*` is local
to this repository. Reuse `bug`, `enhancement`, and `documentation` for type
rather than adding a `type/*` prefix.

## Reporting a broken entry

Open an issue at <https://github.com/burin-labs/harn-packages/issues/new> with
the exact `harn add` command you ran and what it printed. An entry that cannot
be resolved is a production defect, not a documentation bug.
